# Repository Guidelines

Guidance for every coding agent working in this repository. Claude Code loads `AGENTS.md` itself when a project has no `CLAUDE.md`, so this is the only rules file: do not add a `CLAUDE.md` or `.claude/CLAUDE.md` beside it (other agents then ignore it and warn).

## What this is

CrateMind is a local-first, single-user DJ intelligence layer. It scans a music library, lets the user attach **taste metadata** (energy/intensity/darkness/set role/status/substyle/…), finds duplicates, builds sets with a transparent recommender, plays two decks with a djay-style mixer and a Numark Mixtrack Platinum FX controller, and exports artifacts (M3U8 / CSV / JSON backup / Markdown).

**Data-safety invariant (the product's reason for existing):** CrateMind owns *taste metadata only*. It must never delete, move, or retag source audio, and never touches beatgrids or cue points in DJ apps, and never writes to, moves or locks DJ-app files. An opt-in import may read them: the library database from a private copy, and per-track analysis files in place, read-only. Scans are read-only; exports write to the configured output dir, never the source library. Duplicate detection flags groups for review and never auto-deletes. Treat any task that implies mutating the music library as a bug unless the user explicitly asks. Tests and QA must never touch real user data (the live dataset or djay files).

## Runtimes

- **Web (development):** FastAPI backend on `:8000` plus the Vite frontend on `:5173` (proxies `/api`). Both must run together. The web backend answers only to its own hostnames and refuses writes whose `Origin` is foreign (`app/web_guard.py`; `CRATEMIND_ALLOWED_HOSTS` adds exact hostnames). The Vite `/api` proxy vouches for pages it serves by rewriting their `Origin` (`fronts` in `vite.config.ts`, `lib/devProxyOrigin.ts`).
- **Desktop:** Tauri 2 shell in `native/` with the backend frozen by PyInstaller as a sidecar (`backend/packaging/desktop.spec`, which bundles librosa/SciPy/numba for local BPM/key analysis; Essentia and provider jobs stay web-only). MIDI (the controller) is handled by the native shell and exists only in the desktop app. macOS preview build: see `docs/TAURI_DESKTOP_OPERATIONS.md`. An unsigned Windows x64 one-click installer (Velopack `Setup.exe`, per-user, no admin) and its update feed are built by `.github/workflows/windows.yml` on pushes to `windows-build` and on `v*` tags (tags also publish a GitHub Release). Installed Windows apps download newer releases in the background and install them when CrateMind closes (`native/src-tauri/src/updates.rs`; see the operations guide). The same workflow builds a Developer ID signed, notarized macOS arm64 DMG for every tag (signing secrets: see the operations guide).
- **Shared library:** the web runner can use the desktop dataset folder via `CRATEMIND_DATASET_ROOT`; a dataset lease then allows only one app at a time.

## Build, Test, and Development Commands

Backend (FastAPI, Python ≥ 3.12, uv):

```bash
cd backend
uv sync
cp ../.env.example .env                            # set CRATEMIND_LIBRARY_ROOTS
uv run uvicorn app.main:app --reload --port 8000   # API docs at /docs
uv run pytest                                      # all tests
uv run pytest tests/test_search.py::test_name      # one test; -k <keyword> by keyword
```

Backend tests are hermetic: `tests/conftest.py` clears `CRATEMIND_*`, sets `NO_CRATEMIND_ENV_FILE=1` and points every data path (including djay sources) at throwaway temp paths. Keep it that way; never let a test resolve the developer `.env`, the live dataset or djay files.

Frontend (React 19, TypeScript, Vite 8, Tailwind v4, bun):

```bash
cd frontend
bun install
bun run dev          # :5173
bun test             # unit tests in frontend/tests
bun run build        # tsc --noEmit && vite build (also the type check)
```

Desktop schema/route checks after backend changes:

```bash
python3 scripts/desktop/generate_schema_contract.py --check   # regenerate without --check after a schema change
python3 scripts/desktop/check_parity_inventory.py             # every new route must be classified here
```

`.github/workflows/checks.yml` runs the backend tests, these two checks and the frontend tests on every push to `main` and on pull requests. `python3 scripts/third_party_licenses.py --flags` lists everything the desktop bundle ships that is not permissively licensed (read-only; run it before a release). `--check` is the CI licence gate (job `licences` in `checks.yml`): it fails on a flagged entry that is not in `scripts/third_party_licenses_allowlist.json`; add a row there, with the reason, only when the licence suits a GPL-3.0-only build (on the owner's Mac it flags master_me by design). `.github/workflows/osv-scanner.yml` reports known vulnerabilities in the lockfiles weekly and never fails a run.

## Architecture

### Backend (`backend/app/`)
Layered: `api/` routers → `services/` logic → `models.py` (SQLModel) + `db.py` (engine, FTS, backup). Routers mount under `/api` in `main.py`/`app_factory.py`. `config.py` is env-driven (`pydantic-settings`, `CRATEMIND_*` vars, `lru_cache`d settings; look settings up per call, never bind them at import).

- **`db.py`:** SQLite in WAL mode. `init_db()` is idempotent (tables, pragmas, the `track_search` FTS5 table). `backup_on_launch()` snapshots the database at most once per rolling 24 hours, and always before a pending schema upgrade when the library lives in a dataset folder; it keeps `backup_keep` bundles (default 3; on desktop the `cratemind-backup-keep` preference, exactly "1" to "7", set in Settings and read at launch by `config._apply_desktop_backup_keep`). FTS is kept in sync manually via `reindex_track()` / `reindex_all()`: call these after any write that changes searchable columns.
- **`models.py`:** `Track` is the spine (`id` primary key, unique `absolute_path`); `quick_hash`/`full_hash`/Chromaprint `Fingerprint` give content identity. `TrackDJProfile` (1:1) holds the taste axes. Other tables: `Tag`/`TrackTag`, `DuplicateGroup(+Track)`, `DJSet`/`SetTrack`, `TrackPairNote` (transition memory), `PlayEvent`, `AuditLog`, `Job`, `SavedSearch` (Memory Crate), `track_cues`, `TrackBeatgrid` (one row per source: the djay import, and CrateMind's own detected grid), `TrackDownbeat` (user downbeat), `TrackStructure` (sections and phrase lines), `TagWrite` (`tag_writes`: the tag writer's record and undo bytes; `track_id` nullable, `ON DELETE SET NULL`). Any schema change needs the regenerated schema contract. `ArtistProfile.normalized_name` is the artist key every reader joins on through `tracks.artist_normalized` (recommender, search's `artist_*:` and `substyle:`, `artist_substyle`, research): `services/artist_catalog.py` writes today's key (`normalize_primary_artist_name`) while «Καθαρά ονόματα» is off, and `"act:" + names_store.act_key(track_names.folder)` while it is on (NULL for an open or no-artist row, today's key for a track without a row). Both key sets stay in `artist_profiles` (the inactive one at `track_count = 0`); a rebuild never deletes or re-points a profile or review. A new key copies one old profile and its review only when that old key gave it more tracks than any other (no tie) and more than half of the old key's tracks went to it (`carry_sources`); everything else starts without a finding. The legacy re-key never takes an `act:` profile. Besides the scan and «Ενημέρωση λίστας», a names run that ends `done` with the switch on (`names_store.run_job`, before the job row is finished and holding no queue lock) and every switch change (`names_show.set_switch`) rebuild through `artist_catalog.rebuild_quietly`, and the switch refuses to turn (409) while an artist research job waits or runs.
- **`services/search.py`:** the search mini-language (`energy:7-9`, `status:approved`, `bpm:148-155`, `role:peak`, `-retired`, `not_recent:30`, …) compiles to SQLAlchemy criteria; bare words become FTS5 free text. To add a field, extend `_PROFILE_NUM` / `_TRACK_NUM` / `_STR_FIELDS` and the boolean-token handling, and keep `docs/README.md#search-syntax` in sync. `OR` joins a term to the next one; `sort:` and `limit:` are pulled out of the query before filtering and `limit:N` is applied inside `_build_query`, so every consumer (counts, saved searches, facets, bulk edit) sees at most N tracks. The Library sorts in the browser: with a known `sort:` token it keeps the server's order, and `SORT_FIELDS` in `frontend/src/lib/libraryExtras.ts` must mirror `_SORT_FIELDS`.
- **`services/recommender.py`:** a *transparent* weighted scorer (explicitly "not AI"): every candidate returns positive/negative reasons. Relative tempo fit, Camelot-wheel key compatibility, style (psy_substyle → artist genre → genre tag on a style ladder), a bridge mode aimed at the A–B midpoint, and `TrackPairNote` memory (low ratings penalise); `match` (0–100) is musical fit only. `POST /api/recommend` serves Flow Finder without a set. Tempo fit folds a whole octave (`fold_bpm`: half or double within 4% of the target, minus `HALF_DOUBLE_PENALTY`; a 3:4 jump is never folded), and key fit is scaled by `key_weight` (1 for a tag key, a confident own key or djay's key; the confidence for our last-resort key, the one the UI dims with «?»). The eval's `eval.py` must be run with variants that exist in the current scorer; the user's sets hold no half/double pair, so the eval can only show the fold's cost. Re-measure with `.omc/research/recommender-eval` (the user's own sets as ground truth, on a backup copy) before changing weights.
- **`services/beatgrid_detect.py`:** CrateMind's own beat grid from the audio (NumPy only): tempo, beat position, bar line and a confidence; one steady grid, or a beat list of steady sections for a track with a timing jump or a tempo change. It runs as the last phase of `analyze_all` with its own track selection, so a backlog never re-runs BPM, key or providers. `GET /tracks/{id}/beatgrid` serves ours when confident, else djay's. A confident steady grid's tempo is also the track's BPM, second after a manual one (`tracks.bpm_grid`, resolved in `services/tempo.py` and `frontend/src/lib/tempo.ts`, which must stay in step). The grid phase stores the bar vote's share for the chosen beat as `track_beatgrids.downbeat_confidence` (null for djay rows and for grids measured before 2026-11-27, which fill only when the grid is measured again), and the beatgrid route serves it. Below 0.5 (`BAR_LINE_CONFIDENCE_MIN` in `frontend/src/lib/beatGrid.ts`) on CrateMind's own grid without a user downbeat, the deck lane draws its bar numbers with «?» and the DOWNBEAT tool says the bar line is a guess; nothing that counts bars reads the mark. Method, measured accuracy and limits: `docs/BEATGRID_DETECTION.md`; re-measure before changing the method.
- **`services/key_detect.py`:** CrateMind's musical key from the whole track (librosa CQT, log-compressed 2-second blocks, 84 semitones with the octaves kept apart, scored with weights trained on tracks whose key two or three DJ apps agree on; the confidence is the key's probability). It runs in the first analysis pass, whose one whole-track decode also feeds the BPM (first 120 s), and in a key phase of `analyze_all` that re-keys tracks whose `tracks.key_analyzed_method` is older than `key_detect.METHOD`. A track's key is its file tag, then ours when its confidence is at least 0.7, then djay's key (`tracks.key_djay`, mirrored from the djay rows by `djay_import.sync_djay_keys`), then ours at any confidence: `services/musical_key.py` and `fallbackKey` in `frontend/src/lib/camelot.ts` must stay in step. Method, measured accuracy and limits: `docs/KEY_DETECTION.md`; re-measure with `.omc/research/key-eval` before changing it.
- **`services/track_structure.py`:** a track's sections (kick and bass on/off, read from the low end) and phrase lines (every 8 bars from each beat where the bass comes in), measured along CrateMind's own confident grid (NumPy only). It is computed in the grid phase of `analyze_all`, in the same decode (a track whose grid is current is only read for its structure), and stored in `track_structures`. `GET /tracks/{id}/structure` serves it to the Phrase Finder page; `GET /tracks/{id}/beatgrid` adds the phrase lines when it serves CrateMind's grid. With «Χρονισμός από τη δομή» on (`Prefs.transitionStructureTiming`, off by default), the frontend planner times unsaved transition windows from it (`frontend/src/lib/transitions/structurePlacement.ts`; with the switch off, plans must stay as `frontend/tests/transitionPlannerGolden.test.ts` pins them). A bass stop shorter than 12 beats between two bass runs is not a section (unless the run before it is weaker, a build-up), but the bass after it restarts the phrase count when it played six bars up to the stop or came in just before it after a break (since method version 3; version 2 never restarted it), and an anchor one beat off the bar line counts from the bar line. Method version 4 adds build-ups: a bass run of 4 to 32 bars before an entrance is a section with `kind` "buildup" in the row's JSON (rows before version 4 have no kind; no schema change) when both its halves move the low end under 0.75 of the first phrase after that entrance and under 0.8 of the track's usual bass and it is not louder, or when it lies 0.3 under both, its level climbs 0.5 as a line (0.85 of the bars' variance) and the drop starts at least as loud as it ends. Movement is the median of bar means, never of beats (a pattern of strong and weak beats fools that). That entrance is the drop (an anchor, or the end of a 1–2 beat dip on the bar line); a stop of up to 24 beats before it belongs to the build-up, and stays a break before bass that is no build-up. An anchor inside a build-up is dropped and the one at its start is kept, so the count before the build-up is version 3's and restarts on the drop (inside the build-up the lines can move: an entrance version 3 had there is gone). When in doubt the method calls no build-up (a missed one reads as bass; a false one moves «Πρώτο μπάσο», a preset cue and the count): the two movement lines have no gap around them, so re-measure on a fresh sample (`.omc/research/structure-v4-2026-11-27/measurements-2.md`) before moving either. In the frontend `sectionKinds` / `sectionNames` (`frontend/src/lib/trackStructure.ts`) name it «Build-up» and the bass section after it «Drop»; «Πρώτο μπάσο», the preset cues and structure timing follow the first drop, and a build-up still counts as bass for «Δύο μπάσα μαζί» and the set story's bass share. The structure is measured along the track's real tempo octave: a grid an octave off the resolved BPM is folded first (`tempo_factor`/`fold_beats`, the same fold `foldPeriod` in `frontend/src/lib/beatGrid.ts` makes on a steady grid) and the row's JSON records the tempo it was measured at (`bpm`); the only-new grid phase re-reads a structure whose recorded tempo no longer matches, so keep the two folds in step. The owner's hand cues and downbeats are not a reliable reference for this method: never tune it to them or quote agreement with them as accuracy. Method, measurements and limits: `docs/TRACK_STRUCTURE.md`; re-measure before changing the method.
- **`services/playback_loudness.py`:** a track's integrated LUFS and true peak (ffmpeg `ebur128`, read-only), stored on `tracks` (`loudness_*`). Measured in the last phase of `analyze_all` (its own selection: never measured) or on demand by Auto Gain's `GET /tracks/{id}/playback-loudness`; a rescan with a new duration clears it. It feeds the Library «LUFS» column and the `lufs:` search field.
- **`api/history.py`:** play history over `play_events` (`deck`, `ended_at`, `played_seconds` are set only for recorded plays; `played_at` is the start). `GET /history` pages newest first on `(julianday(played_at), id)` with a `before_id` keyset; recording a play bumps `play_count`/`last_played_at`, deleting plays lowers them again; save-as-set builds a `DJSet` in play order.
- **`api/deck_rescue.py`:** deck rescue, the decks' last state as one JSON file in the catalog's cache folder (`cache/deck-rescue.json`, replaced atomically; a file, not a table, so there is no schema change and nothing in backups or exchange bundles). GET answers null for a missing, unreadable, other-version or over-24-hour file and never deletes it; the page writes it and deletes it. `deck_playing()` reads the same file (fresh and both decks loaded) so that `analyze_all` waits between tracks while a two-deck set plays (`audio_analysis._after_decks`).
- **`services/mp3_timing.py`:** a read-only MP3 header reader. Playback (WebKit) and the analysis decode (ffmpeg) skip an MP3's lead-in by different rules, so `lead_in_shift(path)` gives the samples the decode must drop (529, or 1105 with the usual 576-sample encoder delay) or pad with silence (-576 with that delay) for its time zero to be the deck's; it is 0 for anything but an MP3 whose first frame follows its ID3v2 tags directly. Only the grid and structure decodes pass `decode_audio(lead_in=…)`, and `waveform_detail` and the deck lane's density tiles (`waveform_density.py`, from its seek point) shift their own decodes the same way (a non-zero shift enters their digests, so only those tracks get a new etag and are rendered again; the detail into the same cache file); the BPM and key decodes do not, and neither does the overview (`waveform.py`) yet. CrateMind's own `track_beatgrids` rows carry `source_uuid = mp3_timing.TIMELINE`: on a run that is not forced, `_off_timeline_grids` reads the header of each current row without it once (no shift: only marked; a shift: grid and structure measured again; unreadable: left for a later run), so changing `TIMELINE` re-reads every MP3 header. Its frontend twin is `frontend/src/lib/audio/mp3Junk.ts`: `junkBeforeAudio` flags the layout `lead_in_shift` leaves at 0 (ID3v2 tags not followed directly by a frame, which WebKit cannot decode), and `stretchDeck` then fails with `JunkBeforeAudioError` (its Greek message, no retry on `<audio>`). Both files walk back-to-back ID3v2 tags (footer flag included) and test a Layer III frame header the same way: keep the two in step. Measurements: `.omc/research/opendj-comparison-2026-11-24/mp3-timeline/COUNT.md`.
- **`services/tag_writer.py`:** stage 1a of `.omc/plans/2026-11-26-tag-writing.md`, the one module that writes into an audio file: title, artist and genre (`TIT2`/`TPE1`/`TCON` and the same ID3v1 fields) of an MP3's existing ID3v2.3/2.4 block, in place and at the same size. It splices frames with its own walk (every other frame byte for byte in its place, the padding takes the difference) and never uses mutagen's `save`: mutagen only reads. Every check runs on buffers first; the old bytes are on record (`tag_writes` row, `tag-writes.jsonl`, `tag-writes-pending/<id>.bin` beside the catalog) before one in-place `pwrite`, `F_FULLFSYNC` and a read-back; `undo` / `undo_batch` / `undo_logged` reverse the splice, and `restore_pending` runs only when asked. It refuses on Windows (no `pwrite`), while Serato, Traktor or djay runs, and for a `track_id` whose file is not the plan's path. **It has no caller** (no route, job, CLI or startup path) and must not get one until the owner approves the later stages of the plan; `tests/test_tag_writer.py::test_nothing_in_the_app_imports_the_writer` pins that and changes only on purpose. Its tests use MP3s built by hand in `tmp_path` and patch `running_dj_apps`; never point it at a real music file in a test or QA.
- **«Καθαρά ονόματα» (`services/names/`, `names_store.py`, `names_show.py`, `names_decisions.py`, `names_switch.py`; routes `api/names_status.py` and `api/names_decisions.py`; plan `.omc/plans/2026-11-27-name-cleaning-integration.md`, stages 1 and 2):** the deterministic name engine (`services/names/`, ruleset `names-8`, pure: only `names_store.py` imports it, pinned by `tests/test_names_guards.py`) cleans every track's artist and title from its raw tags, and a switch in Settings (off by default, a `name_decisions` row of kind `setting`; `names_switch.is_on` is the one getter) shows the result. **Nothing here writes, moves or retags a file, and nothing writes `tracks.artist/title`.** Data: five `tracks.raw_*` columns (the tags as written, NFC and trimmed, read inside `metadata_reader.read_tags`; `raw_state` NULL = never read, `ok`, `unreadable`; `Field(exclude=True)`, so they are in no payload, and `identity_sync.sync_local_rows` drops them so they never enter the identity library); `name_decisions` (the owner's answers, corrections, «Εντάξει» rows and the switch: user data, in backups, the JSON export and exchange bundles as «Αποφάσεις ονομάτων»; undo sets `revoked_at`, rows are never deleted or rewritten); `track_names` (the result, derived: in `EXCLUDED_VALUE_TABLES`, and a bundle import clears its «Άλλαξαν» columns). The scanner fills the raw columns for new and changed files and, in a delta scan, backfills an unchanged row whose `raw_state` is NULL or `unreadable` (a failed read is retried) by writing only those five columns (no FTS, no hash, no identity re-derive); `merge_tracks` keeps the survivor's raw columns and, where both rows hold an active name decision of one kind, keeps the survivor's and revokes the old row's (never deletes it). A present track with `raw_state` NULL gets no result and shows today's name, and the switch refuses to turn on while one exists. The run (`names_store.run`, job kind `names`) is library-wide: one snapshot, `resolve()`, then one transaction that rewrites only the differing rows; an equal input digest writes nothing, a key-version mismatch among act-scoped answers writes nothing and is named in Settings, and a failed or cancelled run leaves the last rows. Only a missing identity file or `entities` table is a cold library: any other identity read error fails the run (`overlay_off(strict=True)` inside the run), so a locked file is never stored as names. Its record (digest, counts, open and pattern questions, per-answer reach) is `cache/names-run.json` beside the catalog, not a table. The queue is in memory (at most one waiting run, no `jobs` row until it starts, so orphan recovery never drops it); a run waits behind any other job and two playing decks, and a scan or analysis start cancels and re-queues it and is never refused because of it (`_active_job` and `scan_status` ignore kind `names`). Lock order: `worker.submission_lock`, then `names_store._LOCK`, never the other way (`worker.active_job_ids()` takes `submission_lock`, so never call it under `_LOCK`); a starting run stays `queued` until it is `running`. Triggers, only while the switch is on: launch, the end of every scan and analysis job, the identity routes that change links or states (`api/identity.py write_links`), the moved-tracks merge, the legacy import, and every answer, correction and undo; with it off only «Ενημέρωση ονομάτων» and turning the switch on run. A new route that changes links or recording states must call `names_store.request_run("links")`. Showing: `canonical_library.overlay` = `names_show.apply(overlay_off(...))`; `overlay_off` is the old projection and must stay exactly that (the switch's off position, the engine's "shown before" input and `off_*` read it). With the switch off every list, detail, search and export payload equals main's: re-run `.omc/research/name-cleaning-2026-11-27/integration/switch_off_identity.py` after touching the overlay, `db.reindex_track` or `search.py` (it compares JSON with sorted keys; key order follows SQLAlchemy's column loading and is not stable). With it on, `artist`/`title` are replaced and `names_status`/`names_off` added; BPM fields, `original_*` and provenance are untouched; status `none` stores `artist = ''` and shows «Άγνωστος καλλιτέχνης»; a row with no engine title keeps today's title; FTS holds both spellings and `artist:` also matches the shown artist. The `names:` tokens (`docs/README.md#search-syntax`) read the stored rows whatever the switch says (on purpose: Settings' count links work with the switch off; the tokens are new, so no search of before changes). Exports, server-side order, `limit:N`, /tag's cursor, the identity pages, «Μετακινημένα κομμάτια» and the «Καλλιτέχνες» tab still use the stored names (stages 4 and 5). Hand corrections: each track has at most one track decision per run, the latest explicit action wins (a /names correction, a /canonical `edit` copied as a `canonical` row by `write_links` or by the next run, a /canonical accept state built per run and never stored; a /canonical pattern accept, `bulk_accept`, names only tracks without a stored correction); decisions are inputs only, so a scan, a merge, a run or a new ruleset never changes them. `names_decisions.correct` writes the track's row at once (status `hand`), the full run follows. A count in SQL is `names_show._count_where`, never `func.sum(<boolean>)` (SQLAlchemy reads that back as a boolean). Rule ids never reach the UI, with one exception the owner asked for: the inspector's «Γιατί αυτό το όνομα» block prints «κανόνας N7» in small type beside each sentence (`names/explain.py` docstring). `track_names.folder` is advisory: the app never acts on it, it is the input of the later folder move (stage 3, not built), and after that move it drifts from disk as answers and rulesets change; a folder the move made is CrateMind's own output, so the engine's folder evidence can echo a name taken from a link after the link is undone (a listed follow-up). The status words exist three times (`names/explain.py`, `names_show.py`, `frontend/src/lib/namesLabels.ts`; `tests/test_names_words_twin.py` compares them). The owner's research answers are imported once with `reconciliation/names_import.py` (`--dry-run` on a bundle copy, `--apply` with its own verified backup, app closed), never from the app. Frontend: Settings «Καθαρά ονόματα» (`components/NamesSettings.tsx`, which clears `libraryListCache` when the switch turns), the why block (`components/NameWhy.tsx`), the Library's `names:` chips (`components/NamesQuickFilters.tsx`, shown only while the switch is on) and the page «Καθαρισμός ονομάτων» (`/names`, `pages/Names.tsx`, `components/names/`); a bulk «Εντάξει» there always counts with `dry_run` first and writes only after the confirmation. Pages fetch on mount and a deck keeps the names it loaded until its next load. Older builds: after this build opens a library, 0.7.0 still opens it but refuses its exchange bundles (unknown table `name_decisions`), and a scan by a build without the `raw_*` columns (0.7.0, or an older web runner on the shared dataset) updates tags but leaves `raw_*` as they were with `raw_state = 'ok'`, so names come from stale tags until a «Πλήρης σάρωση»: run the web runner on this code once the desktop app is. Measurements and proofs: `.omc/research/name-cleaning-2026-11-27/integration/`; re-measure the equality with `preview-all.csv` on the pinned inputs before changing the engine or the snapshot.
- **`services/djay_import.py`:** read-only djay Pro import (analysis format v8, 4/4). Copies `MediaLibrary.db` + `-wal` (never `-shm`) to a private temp dir, never opens the live DB, reads `.djayMetadata` plists in place.
- **`services/waveform_detail.py`:** CMWD v2 binary detail waveform (RMS/peak envelopes plus frequency RGB colours; NumPy only, no SciPy). `waveform_color.py` computes the colours and `waveform_density.py` renders the per-tile signed-PCM density texture. The stored colours are djay's model (hue = which band leads, saturation = how much, value = level) and are never re-analysed for display: «Χρώματα κυματομορφής» (`Prefs.waveformPalette`) only chooses how the frontend paints them. "frequency" («djay (συχνότητες)») draws the stored RGB; "theme" («CrateMind», the default) repaints it in the app's hues through `frontend/src/lib/wavePalette.ts` (OKLCH: violet lows, lime mids, amber highs, rose where kick and hats meet; a dark and a light set). Every renderer (`DeckScrollWaveform`, `SpectralOverview`, `TransitionWaveform`) takes its colours from `waveformColor` with a `WavePaletteId` from `wavePaletteId(pref, theme)`, and that id is part of every tile and bitmap key (`tileKey` in `lib/deckScroll.ts`); the transition editor's lanes are a dark screen in both themes and always use the dark set. A palette whose hues follow the stored wheel in the same order looks like the djay colours on real music (the old one did: mean hue shift 7°); measure a new map with `frontend/tests/waveformPalette.test.ts` and the method in `docs/DJAY_WAVEFORM_TUNING.md`.
- **«Η κυματομορφή ακολουθεί το EQ»** (`Prefs.waveformFollowEq`, off by default; `frontend/src/lib/waveEq.ts`, `waveEqTile.ts`): on the two big scrolling lanes only, a deck's LOW / MID / HIGH fade that band's colour out and dim the column. Nothing is analysed or fetched again: `bandShares` reads level, saturation and hue back from the stored colour and solves for the lows / mids / highs shares (the six filter hues folded in pairs), `eqColor` mixes them again with each band's gain, and `recolourTile` draws one row of colours over the tile's own pixels with "source-atop" (the alpha, so the shape, never changes). The lane reads the mixer once per drawn frame, recolours a visible tile only when its EQ key (tenths of a dB) changed, at most once per 12 ms, and while a transition owns the deck or the deck has played for half a second it adds the engine's transition stage (`StretchDeck.automationEq`), only while that engine is sounding (`laneEqKey`: not paused, no scheduled start pending), because a paused or silent stage keeps reporting its last curve values in WebKit. TRIM, FILTER and the faders play no part. With the setting off the lane takes today's path: no tile carries the extra field and nothing is read per frame; toggling it clears the lane's tiles. Limits: no reshaping; one colour per column, so a mixed column dims as a whole; a column at full level may have been louder than the stored scale holds; the seek overviews and the transition editor are not affected. The hue, power, saturation, grey and level constants exist in `waveform_color.py` and in `waveEq.ts`: `frontend/tests/waveEq.test.ts` reads the Python file and fails when one side changes. Measured in a WKWebView on 2026-11-28 (2048 × 400 tiles): a recolour keeps every alpha byte, a return to flat is within 2 of 255 of the first colours on pixels at least half opaque and within 4 on fainter edge pixels, one tile costs about 1 ms (plus 0.3–0.4 ms for its row of colours, timed under bun), and recolouring three tiles on every frame dropped no frame; with the real `recolourTile`, six 2048 × 200 tiles (both lanes during a transition) recoloured on every frame took 3–4 ms of main-thread work a frame against 1 ms without, with no frame over 20 ms in 300; re-measure before moving the work onto every frame of a still EQ.

### Frontend (`frontend/src/`)
React + react-router. `app/App.tsx` maps the routes to `pages/` (Dashboard, Library, Artists, Crates, Playlists, «Χαρακτηρισμός tracks» `/tag` (the tagging page, `pages/TaggingQueue.tsx`), Set Builder `/sets`, Flow, Energy maps, Key harmony, Tag cloud, Phrase Finder, Duplicates, Settings, plus capability-gated collection pages). `lib/api.ts` is the single typed fetch wrapper (`req<T>`); `lib/types.ts` holds shared route-level types. Tailwind v4 via the Vite plugin (config in `src/index.css`). `components/ui/` is the glass design system; `components/layout/` is the shell and sidebar. Two-deck playback uses the Signalsmith Stretch WASM worklet (`lib/audio/stretchDeck.ts`); the deck waveform panels portal from `MiniPlayer` into `DeckViewSlot`. The deck engine's 160 ms schedule lead (`latency() + LEAD_MARGIN` in `stretchDeck.ts`) is measured, not slack: the vendored worklet takes a schedule the moment it arrives and needs about 93 ms after that for a start or a cue jump to land clean, and WebKit's message delay reached 43–122 ms under CPU load (`.omc/research/batch-10-2026-11-27/play-lead-harness`). Do not shorten it toward Open DJ's 55 ms without re-running that harness: at 55–80 ms starts come in soft and cue jumps carry the old position into the landing point. In two-deck mode each deck has an FX rack: one AudioWorklet node per deck (`lib/fxRack/`, own DSP) sits after the deck's fader and before the master bus, bound by `lib/fxRackHost.ts` (mounted through `useFxRack` in AppShell), which posts the beat clock from the engine's anchor and grid (`lib/fxRackClock.ts`); `lib/fxRack.ts` is its store. Every deck's playback graph feeds one master bus (`lib/audio/masterBus.ts`). Two-deck decks always get a graph. A single-deck `<audio>` element plays natively, outside the bus, until Auto Gain, the Limiter or the Maximizer has been on (the gate in `prepare()` in `lib/usePlaybackProcessing.ts`). After that it stays on the bus for the element's lifetime. Anything new on the bus must also join that gate, with one approved exception: the bus's own always-on safety limiter (`masterBus.ts`, the deck limiter's worklet at -1 dB, after the insert slot; it steps aside while the Maximizer is the insert and is skipped when the worklet cannot load) acts only on what is already on the bus and never moves a native single-deck play onto it. The Maximizer is its insert, driven by `lib/useMaximizer.ts`; its engine is private (see Versioning & Releases) and `lib/audio/maximizer.ts` holds only its contract and `MAXIMIZER_BUILT`, which gates every control. ## Coding Style & Naming Conventions

Python: simple modules with focused service functions and FastAPI routers. Prefer `pathlib`, structured parsing, SQLModel models and explicit error handling. Keep side effects obvious, especially around scanning, exports and file access.

TypeScript React function components. Page components use PascalCase filenames, shared helpers use camelCase, and route-level data types belong in `frontend/src/lib/types.ts` unless they are local to one component.

All user-facing UI copy must be in Greek: labels, buttons, headings, tooltips, toasts, error messages and report text. Use English only when no Greek word is a good match, such as `beatgrid`, `downbeat`, `BPM`, `M3U8`, `tag` or `export`. Never show internal keys or English reason codes (`non_straight`, `missing`) to the user; map them to Greek text.

## Testing Guidelines

Backend: `pytest`, files named `test_*.py` in `backend/tests/`. Add tests for scanner idempotency, parser behaviour, duplicate safety, recommender scoring, exports, data-safety guarantees and API regressions; build fixtures by hand, never from personal data. Frontend: `bun test` for pure helpers in `frontend/tests/`, and `bun run build` for type/build validation.

A check that cannot measure reports UNKNOWN, never a pass: a test, harness, QA script or CI gate that finds no input, no tool or no data says so (a skip with its reason, a non-zero exit, «UNKNOWN» in the report) instead of passing quietly, and a report never counts it as checked. Every pair this file says must stay in step (a backend function and its frontend twin, such as `services/tempo.py` and `lib/tempo.ts` or `musical_key.py` and `camelot.ts`, or one constant in two files) gets a test that feeds both sides the same vectors or compares the two values, so a change to one side fails until the other follows; add it with the pair.
